## Top 3 real risks for this app

1. **Default admin credentials shipped and publicly advertised** — `seed.sql:26-28` bakes in `admin@kopikita.id / kopikita-admin` and `login/page.tsx:88-89` prints it on the login screen. Anyone reaching a seeded deploy gets full CMS control (create/update/delete products, read all customer bookings with phone numbers). Reason: the credential is literal source + UI text, so it is discoverable without any exploit, and there is no forced password change.
2. **No login throttling or lockout on the single admin account** — `routes/auth.ts:14-56` has no rate limit, backoff, or lockout, and failed attempts are not logged (`auth.ts:24,31`). Reason: with only one admin identity and a documented default credential, online brute force / credential stuffing is cheap and completely undetected; there is no second factor either.
3. **Unauthenticated `POST /api/bookings` has no abuse controls** — `routes/bookings.ts:8` is public and unthrottled. Reason: it lets anyone flood the bookings table (fake reservations the staff must triage) and generate write load against the shared DB connection pool (`src/server/db.ts:18` `max: 10`), a realistic availability/spam risk for a small café app with no CAPTCHA or rate limit.
